# Protocol v1.1 — Authorization records and deterministic MsgSend semantics

`alpha` is the canonical owner of this contract. The middleware keeps an identical
copy. Any protocol change requires an ADR, a `CONTRACT_VERSION` bump, and contract
synchronization from Alpha to middleware.

This revision clarifies the semantics required by M2. It does not introduce the
signed-batch implementation itself.

## 1. V1 functional scope

V1 authorizes only direct:

```text
/cosmos.bank.v1beta1.MsgSend
```

`authz.MsgExec`, IBC transfer, smart-contract calls, per-transaction certificates,
ZK proofs, and nested-message authorization are outside V1 M2 scope.

A transaction containing multiple direct `MsgSend` messages must authorize each
direct `MsgSend` independently. Other message types are not interpreted by the
M2 evaluator.

## 2. AuthorizationRecord V1

The logical record schema is:

```text
authorization_id: string
subject: string
msg_type_url: string
policy_id: string
policy_version: uint64
issuer_set_id: uint64
valid_from_height: int64
valid_until_height: int64
revoked: bool
bank_send_constraints {
  denom: string
  receiver: string
  max_amount: string
}
```

### Field semantics

- `authorization_id`
  - opaque identifier generated by the trusted off-chain authorization layer;
  - non-empty;
  - used for audit/correlation and later stale-revocation protection;
  - NOT the primary lookup key for normal user transactions;
  - a new grant replacing the current grant for the same logical key SHOULD use
    a new `authorization_id`.

- `subject`
  - canonical bech32 account address;
  - for MsgSend it MUST equal `MsgSend.from_address`.

- `msg_type_url`
  - for V1 M2 MUST equal exactly:
    `/cosmos.bank.v1beta1.MsgSend`.

- `policy_id`
  - non-empty identifier selected by the trusted policy layer, never by the
    requester.

- `policy_version`
  - unsigned integer greater than zero;
  - metadata attached by the trusted policy layer.

- `issuer_set_id`
  - unsigned integer greater than zero;
  - identifies the issuer set that will later authenticate the batch carrying
    this record.

- `valid_from_height`
  - positive block height;
  - inclusive lower bound.

- `valid_until_height`
  - positive block height;
  - inclusive upper bound;
  - MUST satisfy `valid_until_height >= valid_from_height`.

- `revoked`
  - if true, authorization is denied regardless of all other fields.

- `bank_send_constraints.denom`
  - non-empty SDK-valid denom;
  - exact, case-sensitive match.

- `bank_send_constraints.receiver`
  - canonical bech32 account address;
  - exact match with `MsgSend.to_address`.

- `bank_send_constraints.max_amount`
  - canonical positive base-10 integer string;
  - no sign, no decimal point, no exponent, no leading zeroes;
  - regex-equivalent form: `[1-9][0-9]*`;
  - never float.

`policy_hash` is NOT part of AuthorizationRecord V1. It belongs to the signed
batch metadata.

## 3. Logical lookup key

The authoritative logical lookup key for a normal user transaction is:

```text
(subject, msg_type_url)
```

V1 maintains exactly one CURRENT AuthorizationRecord for a logical lookup key.

`authorization_id` is metadata, not part of the normal lookup key.

The physical Cosmos KV encoding of this tuple is an Alpha implementation detail,
but it MUST be deterministic and O(1)-style to retrieve.

No store scan is allowed in the normal MsgSend authorization path.

## 4. Upsert and revoke semantics

M2 MUST NOT expose a public unauthenticated transaction that lets arbitrary users
write AuthorizationRecords.

During M2, records may be inserted through:
- genesis/test setup;
- internal Keeper methods needed by tests and future authenticated handlers.

The public authenticated mutation path is introduced by the signed-batch
milestone.

After signed-batch verification exists, a valid upsert for an existing logical
key replaces the CURRENT record at that key.

Revocation MUST NOT be implemented as silent deletion. Revoking the current grant
sets/persists `revoked=true` (or an equivalent auditable current-state
representation). A later explicitly authorized new grant may replace that revoked
current record with a new `authorization_id`.

## 5. Direct MsgSend shape

V1 M2 supports a direct `MsgSend` with exactly ONE positive Coin in `amount`.

Therefore:

```text
len(MsgSend.amount) == 1
```

is required.

Multi-coin MsgSend is outside V1 M2 and MUST be rejected deterministically with:

```text
AUTHZ_UNSUPPORTED_MSG_SHAPE
```

The supported Coin amount must be a positive integer.

## 6. Deterministic evaluation semantics

For a direct MsgSend, the authoritative evaluator uses only:

```text
current block height
+ MsgSend fields
+ committed AuthorizationRecord
```

No TCP, HTTP, RPC, Keycloak, SQLite, gossip, local wall clock, filesystem, or
subprocess may influence the result.

The deterministic evaluation order is:

1. Validate supported direct MsgSend shape.
   - failure -> `AUTHZ_UNSUPPORTED_MSG_SHAPE`

2. Lookup current record by:
   `(MsgSend.from_address, "/cosmos.bank.v1beta1.MsgSend")`
   - missing -> `AUTHZ_NOT_FOUND`

3. Validate stored record consistency.
   - malformed/inconsistent -> `AUTHZ_INVALID_RECORD`

4. If `revoked == true`
   - -> `AUTHZ_REVOKED`

5. If `current_height < valid_from_height`
   - -> `AUTHZ_NOT_YET_VALID`

6. If `current_height > valid_until_height`
   - -> `AUTHZ_EXPIRED`

7. Require exact receiver match.
   - mismatch -> `AUTHZ_RECEIVER_MISMATCH`

8. Require exact denom match.
   - mismatch -> `AUTHZ_DENOM_MISMATCH`

9. Parse `max_amount` as the canonical positive integer defined above and require:

   ```text
   MsgSend.amount[0].amount <= max_amount
   ```

   - greater -> `AUTHZ_AMOUNT_EXCEEDED`
   - malformed stored amount -> `AUTHZ_INVALID_RECORD`

10. Otherwise:
    - -> `AUTHZ_OK`

Height validity is therefore inclusive:

```text
valid_from_height <= current_height <= valid_until_height
```

## 7. Policy metadata during normal user transactions

Normal user transactions do NOT carry a `policy_id`, `policy_version`,
`policy_hash`, or issuer signature.

Therefore the M2 MsgSend evaluator MUST NOT invent a comparison against
request-supplied policy metadata.

In V1:

- `policy_id` and `policy_version` are trusted record metadata;
- policy consistency and issuer scope are checked when authenticated record
  updates are accepted;
- changing a policy does not automatically invalidate all already-committed
  records unless they are explicitly revoked/replaced or expire.

`AUTHZ_POLICY_MISMATCH` is reserved for update/batch validation paths where two
policy references are actually being compared. It is not part of the normal M2
MsgSend decision path.

## 8. Middleware record construction

The requester never selects the policy.

The trusted middleware flow is:

```text
normalized MsgSend facts
        +
validated PolicyDecision
        +
trusted build context
        ↓
AuthorizationRecord
```

The PolicyDecision/trusted authorization layer supplies or determines:
- `policy_id`;
- `policy_version`;
- `issuer_set_id`;
- allowed typed constraints;
- authorization validity policy.

The requester MUST NOT directly choose these values.

If absolute heights are materialized from a policy-selected validity window, the
trusted gateway may combine:
- a chain height observed off-chain;
- a policy-selected validity duration/window.

The resulting record MUST contain absolute:
- `valid_from_height`;
- `valid_until_height`.

No wall-clock value is serialized into these fields.

The AuthorizationRecord builder:
- MUST reject a deny decision;
- MUST reject incomplete/invalid trusted metadata;
- MUST fail closed on errors;
- MUST NOT call Keycloak, SQLite, gossip, or Cosmos as part of the pure build
  operation itself;
- MUST NOT become a second policy engine.

## 9. M2 mutation security boundary

Because batch signatures/quorum are not implemented yet, M2 MUST NOT add a
general-purpose public `MsgSetAuthorization` or equivalent bypass.

A Keeper-level setter may exist for:
- genesis;
- tests;
- future authenticated batch handler use.

User-controlled authorization creation begins only after the authenticated batch
path is implemented.

## 10. Batch V1 baseline for later milestones

Batch fields:

```text
domain = "alpha.authzattrs.batch.v1"
chain_id
batch_id
policy_id
policy_version
policy_hash
issuer_set_id
records[]
signatures[]
```

Required types/semantics for the fields already fixed by this revision:

```text
batch_id: uint64
policy_version: uint64
issuer_set_id: uint64
```

Within one batch:
- every record MUST match the batch `policy_id`;
- every record MUST match the batch `policy_version`;
- every record MUST match the batch `issuer_set_id`.

### Canonical ordering

Before deterministic protobuf serialization/signing, records are sorted by:

```text
(subject, msg_type_url)
```

A batch containing more than one record for the same logical key
`(subject, msg_type_url)` is rejected with:

```text
AUTHZ_BATCH_DUPLICATE_RECORD
```

There is no last-write-wins behavior inside one batch.

### Anti-replay baseline

`batch_id` is monotonically increasing per `issuer_set_id`.

The chain stores the highest successfully applied `batch_id` for each issuer set.

A batch is valid only if:

```text
batch_id > last_applied_batch_id[issuer_set_id]
```

Otherwise reject with:

```text
AUTHZ_BATCH_REPLAY
```

The exact deterministic protobuf sign-byte schema and signature verification are
implemented/frozen in M3.

## 11. Quorum baseline

A signature counts at most once per issuer.

An issuer must be:
- registered;
- active;
- valid at current height;
- a member of the expected `issuer_set_id`;
- in scope for the policy/message type;
- cryptographically valid.

Normal user MsgSend does NOT execute these checks. They belong to batch update
verification.

## 12. Golden vectors

Starting with the signed-batch milestone, both repositories must contain identical
golden-vector inputs and expected deterministic sign bytes/hash.

`authzctl contract check` must fail when shared contract copies diverge.
